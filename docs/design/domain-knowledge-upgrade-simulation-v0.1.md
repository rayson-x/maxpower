# 领域知识改造方案：现状盘点、缺口与前后输出模拟

> 版本：v0.1 · 日期：2026-08-10 · 状态：proposal
> 姊妹篇：`agent-harness-and-domain-knowledge-gaps-v0.1.md`（harness 优化）；本文专注领域知识：有什么、缺什么、怎么改、改完用户看到什么。

## 1. 目前提供了什么（按用户可感知的能力）

| 层 | 内容 | 代码位置 |
|---|---|---|
| 动作知识 | 33 动作族 × 器械/变式笛卡尔积目录；主/次肌群（含"预计参与非激活观测"免责声明）；俯卧撑难度图；5 目标替代排序 | `src/knowledge/installedPack.ts:86-360` |
| 训练规则 | 增肌/增力/减脂保肌三规则包：首场 RIR 4–5 校准、双进阶（≤10%）、周量 ±1 直接组、deload 触发与内容、徒手相邻节点进阶 | `src/training-rules/trainingRulePacks.ts` |
| 营养策略 | 蛋白 1.6–2.2 g/kg、脂肪下限 20%、Mifflin-St Jeor 估算（标 provisional）、±200 kcal 有界调整、安全拒绝清单 | `src/nutrition/NutritionStrategyEngine.ts` |
| 恢复约束 | 主观优先决策树、HRV 分设备/算法建基线、四级约束、症状硬暂停 | `src/recovery/RecoveryRulePack.ts` |
| 安全边界 | onboarding 自填禁忌 → stop_and_seek；营养拒绝清单；托管三模式 | `src/onboarding/`、`src/coach/policy.ts` |

**这些都是确定性引擎知识——计划"算得对"。**

## 2. 欠缺什么（按用户会遇到的场景）

| # | 场景 | 缺的知识 | 后果 |
|---|---|---|---|
| 1 | 用户问"这动作练哪/为什么这么安排" | LLM 无知识检索通道（13 工具全是状态查询/提案） | 回答靠模型先验：不可审计、可能与目录矛盾、说法每次不同 |
| 2 | 用户问"依据是什么" | 引擎数值无 evidenceRefs（planningEvidence 仅 1 条 citation） | 审计链断在"产品默认值"，给不出文献级回答 |
| 3 | 新用户说"我想减肥，帮我安排" | 无结构化筛查（PAR-Q 逻辑），只有自填清单 | 风险分层粗糙；筛查对话无章可循 |
| 4 | 用户说"上周没练，是不是废了" | 无行为改变知识（TTM/MI/习惯回路） | 回应质量全看模型运气：可能说教、可能纵容，不会按改变阶段定制 |
| 5 | 用户该被主动关心时 | 无 proactive 知识触发（见 harness 文档 B3） | 教练永远等用户开口 |

**一句话：引擎层"会算"，对话层"不会聊"，知识层"答不出依据"。**

## 3. 改造结构：三层各补什么

```
知识内容层  workspace wiki 知识页 + docs/wiki 知识包
            └─ 补：行为改变知识页（先完成 13 条待验证断言核验）
                  补：PAR-Q/ACSM 筛查算法知识
                  补：引擎数值 ←→ 文献的 evidenceRefs 挂钩
引擎层      确定性规则（保持"LLM 不决策"）
            └─ 补：结构化筛查决策树（接 OnboardingService）
                  补：knowledge.lookup_exercise / explain_rule 只读工具
对话层      system prompt + 工具清单
            └─ 补：行为改变对话准则（按 TTM 阶段选择互动方式）
                  补：知识工具的强制使用与拒答纪律
```

改造原则：**新增知识全部走"先入库（wiki 知识页，带来源）→ 再接引擎/对话"的路径**，对话层不允许出现知识库里没有的数值。

## 4. 前后输出模拟

> 说明：以下"补充前"按当前架构的真实行为模拟——远程 LLM 无领域知识注入、无知识工具、无对话准则，回答依赖模型先验。"补充后"按本文方案模拟，标注每个差异来自哪项改造。

### 场景 1：用户问「俯卧撑主要练哪里？我可以天天练吗？」

**补充前**（当前架构 + 远程 LLM）：

> 俯卧撑主要锻炼胸大肌、三角肌前束和肱三头肌，同时也会用到核心稳定。至于天天练，要看你的恢复情况，一般建议同一肌群间隔 48 小时。你可以试试每天少量、或者隔天加量……

看起来没问题？问题在于：① 肌群说法来自模型先验，不是产品审核过的目录——目录里 `push_up` 的肌群关联带 `exact_exercise_reference` 证据状态和免责声明，LLM 的回答**无法对账**；② "48 小时"是模型编的常识数字，规则包里没有任何地方定义它——**它在即兴创造数值**，违反"对话层不允许出现知识库没有的数值"；③ 用户当前计划里俯卧撑的周量、最近一次表现、恢复约束都在本地，回答却完全没用到。

**补充后**（启用 `knowledge.lookup_exercise` + evidenceRefs）：

> 〔调用 knowledge.lookup_exercise("push_up")〕
>
> 按动作库的记录：俯卧撑是水平推模式，预计主要参与胸肌、肩前束和肱三头肌——这是动作学参考资料的策展结论，摄像头无法测量你的肌肉实际激活。
>
> 能不能天天练，看你这两天的实际情况：你昨天刚练过胸部推类（3 组 × 12，RIR 约 3），今天的恢复评估正常。如果今天想练，建议保持现有计划不变；连续两天练同一肌群时，我会把今天这组的目标 RIR 上调 1，避免累积疲劳。
>
> 〔依据：动作库 push_up 条目（ACE 动作参考）；周量与恢复规则 TP-VOL-PROG@1 / 恢复决策树〕

差异来源：① 肌群回答挂在审核目录上，附带免责声明（**A2.3 知识工具**）；② 不创造"48 小时"这类库外数字，改为引用用户实际时间线与规则（**A2.3 + 已有恢复引擎**）；③ 依据可被点击追溯（**A2.4 证据回填**）。

### 场景 2：新用户说「我想减肥，你帮我安排一下」

**补充前**：

> 好的！为了给你安排，我需要了解一些信息：你的年龄、身高、体重、有没有运动基础？平时有什么疾病或者伤病吗？

收集靠模型自由发挥：问题清单不可复现；可能漏掉关键禁忌（孕产、进食障碍、用药）；"有没有疾病"这种问法既没有风险分层，也没有"为什么要问"的解释。

**补充后**（结构化筛查决策树 + TTM 阶段评估）：

> 好的，开始之前我需要做两件小事，大约两分钟。
>
> **第一是安全筛查**——这几个问题决定我能直接给你安排，还是需要你先咨询医生：近期有没有胸痛、晕厥或异常呼吸困难？有没有确诊的心脏、代谢或肾脏疾病？目前在孕期或哺乳期吗？有没有正在进行的医嘱饮食或减重药物？（任一"是"，我会给出转介说明而不是训练计划。）
>
> **第二是了解你的起点**：过去一个月，你有规律运动吗？——这决定我们从多保守的计划开始。
>
> 〔依据：ACSM 运动前筛查三变量（Riebe 2015, PMID 26473759）；TTM 阶段评估〕

用户回答后，行为随之分流：高风险 → `stop_and_seek_professional_guidance` 约束 + 转介说明（现有安全机制，但触发自**结构化**输入）；低风险+"还没开始动"（前意向/意向阶段）→ 对话策略进入 evoking 模式而非直接给方案（见场景 3）。

差异来源：**A2.2.1 结构化筛查**（问题集确定、可复现、可审计）+ **A2.1 行为改变准则**（先评估阶段再决定互动方式）。

### 场景 3：用户说「上周三次训练一次都没去，我是不是不适合健身」

**补充前**（两种典型坏法，取决于模型心情）：

> A：「别灰心！每个人都会有这样的时候，这周重新开始就好，加油！」（空洞鼓励，没有改变策略）
>
> B：「坚持很重要。建议你设定固定闹钟，把训练放在日程里，这周务必完成三次。」（说教 + 直接加要求，对动摇期用户是反效果）

**补充后**（TTM + MI 四过程写入对话准则）：

> 一次没练不等于不适合——按计划看，你这周的三次课都还在，没有失效，随时可以改期。
>
> 我更想知道的是：上周是**没时间**，还是**不太想练**？这两个的调整方法完全不一样。
>
> 〔用户答"加班太累"后〕那问题就不是你，是计划没贴合你的日程。两个选项：A. 把下周改成两次 30 分钟的短课，保住连续性；B. 维持三次但允许其中一次只做主项。你倾向哪个？——你选的我再固化成计划。

差异来源：evoking（引出用户自己的原因）→ 给自主选择权（SDT 自主需求）→ 把计划调整包装成用户的选择（**A2.1 对话准则**）；同时"课还在、可改期"来自真实计划状态而非安慰话术。注意全程没有编造任何数值。

### 场景 4：用户问「减脂期你让我每天吃 140g 蛋白，依据是什么？」

**补充前**：

> 减脂期提高蛋白质有助于保留肌肉。一般建议每公斤体重 1.8–2.2 克，你的体重 70kg，所以大约 126–154g，140g 在这个范围内。

合理，但：数值链条（1.8–2.2、× 体重）是模型复述"训练中学到的常识"，**与 NutritionStrategyEngine 的实际计算路径是否一致无法保证**——哪天规则包改成按 FFM 计算，LLM 还在背旧口径，用户看到的就是矛盾。

**补充后**（`knowledge.explain_rule` + evidenceRefs）：

> 〔调用 knowledge.explain_rule("nutrition.fat_loss_preserve_lean")〕
>
> 你的 140g 是这样来的：减脂保肌策略使用每公斤体重 1.8–2.2g 的蛋白区间，你是 70kg，取区间中值附近。
>
> 这个区间的依据：ISSN 立场声明建议健康运动成人 1.4–2.0 g/kg/d；对减脂期、较瘦且训练有素的人，系统综述建议可达 2.3–3.1 g/kg **去脂体重**——我们的 1.8–2.2 g/kg 是覆盖大多数用户的保守产品默认，不是"被研究验证的唯一最优值"。
>
> 它不是精确指标：如果你的实际体脂率较高或较低，或者你有可靠的体成分测量，这个数值得重新校准。
>
> 〔依据：ISSN 2017 PMID 28642676；Morton 2018 PMID 28698222；Helms 2014 PMID 24092765；规则包 nutrition-strategy 当前版本〕

差异来源：回答与引擎**同一条数值链**（**A2.3**）；文献出处可点（**A2.4**）；"保守产品默认，不是最优值"的表述直接来自知识页的"不能推出什么"纪律。

## 5. 改造工作量分级

| 改造项 | 性质 | 量级 |
|---|---|---|
| 行为改变知识页入库 + 对话准则 | 知识 + prompt 策略，无新引擎 | 小 |
| 结构化筛查决策树 | 纯确定性逻辑，接入点已存在 | 小-中 |
| 知识检索双工具 | 只读查询已内嵌的知识包，schema 简单 | 小-中 |
| evidenceRefs 回填 | 知识治理数据工作（PMID 已核对） | 中（繁琐但无风险） |
| 动作筛查（FMS 式） | 受识别 profile validated 数量门控 | 大（长线） |

**前置绑定**：知识工具上线前必须先有 eval 套件（harness 文档 B4）——否则"LLM 是否用对了知识"没有度量。
