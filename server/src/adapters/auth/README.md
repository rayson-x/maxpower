# Production identity composition

Mount `createProductionIdentityStack(config).authHandler` at `/api/auth/*` and
inject the returned `identity` into the V1 HTTP routes. Never mount
`betterAuth.handler` directly.

The reviewed Better Auth handler exposes only:

- the server-owned social authorization bridge and Google/Apple callbacks;
- explicit link/list/unlink operations (link and unlink require a session
  created within the last five minutes);
- the error callback and `/api/auth/.well-known/jwks.json`.

Email/phone OTP and password endpoints are deliberately absent from that
allowlist. They are available only through the stable `/v1/auth/*`
`IdentityModule` contract. Raw Better Auth social sign-in, session, token,
sign-out, and native proxy routes return 404.

## Client credential lifecycle

OTP/password responses return an opaque `sessionToken` and a five-minute
`accessToken`. Store only `sessionToken` in platform secure storage; keep the
service JWT in memory. Call `POST /v1/auth/refresh` with the session token to
replace the service JWT. Every service request verifies the JWT and then reads
the live Better Auth session and user authorization from Postgres, so logout,
expiry, and an account restriction take effect immediately.

For Google/Apple sign-in, create and retain a random 32-byte hex
`deviceBinding` in platform secure storage, then call
`POST /v1/auth/social/start` with the provider, the exact registered native
callback, and that binding. Open the returned HTTPS `authorizationUrl`. The
native callback contains only `code` and `state` on success, or `error` and
`state` on failure. Exchange a successful callback through
`POST /v1/auth/social/exchange` with the original callback URL and
`deviceBinding`; its response is exactly `{ "sessionToken": "..." }`. Then use
the normal `POST /v1/auth/refresh` flow.

The server binds provider, OAuth state, callback target, and a digest of the
device binding. It stores only a digest of the short-lived exchange code and
consumes it atomically, so a captured custom-scheme callback is unusable from a
different device and replay returns 409. Better Auth state/session cookies are
handled only inside the HTTPS callback and are never forwarded to a native URL.
First-time restricted social users finish with
`POST /v1/auth/social/complete`; existing accounts must use reviewed
`POST /api/auth/link-social` after fresh reauthentication. Matching email alone
never links identities.

## Auditing the schema migration

`better-auth.cli.ts` is a schema-only configuration with an OTP delivery port
that always fails. The checked-in SQL body was generated by the pinned official
CLI and then wrapped in the outer transaction required by the migration runner:

```sh
docker run -d --rm --name maxpower-better-auth-schema \
  -e POSTGRES_USER=schema -e POSTGRES_PASSWORD=schema -e POSTGRES_DB=schema \
  -p 127.0.0.1:55432:5432 postgres:17-alpine

BETTER_AUTH_SCHEMA_DATABASE_URL=postgres://schema:schema@127.0.0.1:55432/schema \
  npm exec --yes --package=auth@1.6.26 -- auth generate \
  --config ./src/adapters/auth/better-auth.cli.ts \
  --output /tmp/maxpower-better-auth.sql --yes

docker stop maxpower-better-auth-schema
```

Compare `/tmp/maxpower-better-auth.sql` byte-for-byte with the contents between
`BEGIN;` and `COMMIT;` in `migrations/010-better-auth.sql`.
